# DeutschConnect
Cross-school collaboration platform
# AGENTS.md – DeutschConnect

## Project context

Before making changes, read `README.md` to understand the project's purpose, current status, priorities, and constraints.

DeutschConnect is a student-led, cross-school collaboration platform being developed for an initial pilot between Ernst-Reuter-Schule Ankara and Anka Bilim.

The immediate goal is a functional, responsive web prototype that supports the organization of real cross-school activities.

## Working rules

1. Inspect the existing repository before creating, deleting, or modifying files.
2. Do not assume that planned features are already implemented.
3. Prioritize the MVP described in `README.md`.
4. Do not implement future modules unless explicitly requested.
5. Prefer simple, maintainable solutions suitable for student developers.
6. Use React, Vite, JavaScript, and CSS as the preferred stack for a new implementation, unless existing project files justify a different approach.
7. Reuse existing functional components instead of unnecessarily rewriting them.
8. Do not introduce major dependencies or architecture changes without explaining why they are needed.
9. Keep the interface responsive and accessible.
10. Use fictional sample data until real data handling has been approved.
11. Do not implement private messaging or public student profiles without explicit authorization and appropriate safeguards.
12. Never expose credentials, API keys, or sensitive personal information.
13. Do not deploy publicly or perform destructive operations without explicit permission.
14. Run available relevant checks after changing code. Do not invent test commands that the project does not support.
15. Document important architectural decisions and remaining limitations.
16. Distinguish clearly between working functionality, mock functionality, and future plans.
17. Preserve the existing Git history and avoid unnecessary project recreation.
18. Keep changes focused on the specific task requested.

## Communication

Explain implementation decisions and errors in German, using English technical terminology where useful.

The project owner is still learning web development. Provide concise explanations of important concepts and commands.

Avoid unnecessarily lengthy output when a short summary is sufficient.

## Efficient Codex usage

The team has limited development time and wants to avoid unnecessary Codex usage.

Before implementation, identify the smallest set of changes required to accomplish the task.

Prefer targeted modifications over rebuilding the entire application.

When a task is completed, summarize:

- What was changed
- Which files were affected
- Which checks were performed
- What works
- What remains incomplete
- What should be done next

## Definition of done

A task is complete only when its requested functionality is implemented, relevant available checks pass, and important limitations are reported.

Do not claim that a feature has been tested if it has not actually been tested.

## Primary priority

Build a small, reliable platform that enables a real cross-school collaboration between ERS and Anka Bilim.

**Real functionality and demonstrable impact are more important than the number of features.**

Before implementing the UI, inspect all available screenshots in docs/design-references/ and read section 21 of README.md. Use the original dark navy design, blue accents, rounded cards, filter chips and navigation patterns as visual references. Adapt the old course and tutor interface to the new cross-school events, ideas and collaboration platform. Do not copy the original commercial business model, fictional statistics, account information or unsupported partnership claims. Prioritize a mobile-first responsive web application, with complete German, Turkish and English localization.
